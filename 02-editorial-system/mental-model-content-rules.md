# Mental Model Content Rules

## Purpose of this file
Use this file to approve or reject free content ideas before they become carousel briefs.

This file now works under the higher standard in `02-editorial-system/thought-leadership-doctrine.md`. Free content should not be only mental-model-led. It should be **argument-led mental-model content**: a clear operator argument supported by diagnosis, evidence where relevant, antithesis, mechanism, application, behavior shift, and a platform action objective.

## Required structure for every free post
Every free content idea should include:

1. **Exact operator problem** — the messy work situation the audience recognizes.
2. **First-principles cause** — why the problem exists structurally, not just how it shows up.
3. **Evidence / data / example, where relevant** — a credible data point, research finding, public example, concrete mini-case, or observable workplace pattern that supports the argument.
4. **Common false solution** — the default fix people try that is incomplete.
5. **Antithesis** — the contrast between default behavior and high-leverage operator behavior.
6. **Hidden mechanism** — the unseen process that explains why the problem repeats or why the better behavior works.
7. **Framework** — the reusable way to think about the issue.
8. **Applied example** — a simple realistic situation showing how the model changes the work.
9. **Behavior shift** — the operating question, habit, or lens the reader should adopt.
10. **Primary action objective** — the platform action the post is mainly designed to create: save, share, comment, profile visit, bio click, or product interest.

## Editorial rules
- Start with the work problem, not the tool.
- Diagnose before prescribing.
- Teach the thinking before mentioning implementation.
- Make the hidden flaw specific enough to feel diagnostic.
- Explain why the problem exists, not only what to do about it.
- Use one clear central argument per post.
- Use a mental model only when it explains a mechanism, not when it merely renames obvious advice.
- Use evidence where it strengthens trust; use concrete examples when strong data is unavailable.
- Include antithesis so the reader can see the gap between default and high-leverage behavior.
- Keep examples practical and operator-grade.
- Keep AI as leverage, not decoration.
- Separate free teaching from paid implementation.
- Define the intended platform action before drafting.

## What this prevents
- Generic listicles
- Generic AI tips
- Tool-first tutorials
- Prompt dumps
- Decorative frameworks
- One-dimensional advice with no contrast
- Evidence-free claims presented as doctrine
- Text-heavy advice posts with no structure
- Ultra-minimal slides that look clean but say little
- Motivation without method
- Founder hustle content
- Corporate jargon without operator utility

## Quality test
Approve an idea only if it passes most of these questions:

1. Does it begin with a real operator pressure?
2. Is the exact problem specific enough to feel recognized?
3. Is there a first-principles cause, not just a surface complaint?
4. Is there a hidden thinking flaw, not just a broad frustration?
5. Is there evidence, data, research, a credible example, or a concrete workplace pattern where relevant?
6. Is the common false solution named?
7. Is there a respectful antithesis between default behavior and stronger operator behavior?
8. Does the framework explain why the problem happens and where value leaks?
9. Can the mental model be reused in more than one situation?
10. Can the idea be explained visually through an argument path?
11. Would the post still work if no tool was named?
12. Does the free version improve thinking, diagnosis, communication, decision quality, or operating behavior?
13. Is the intended action objective clear?
14. If there is a paid bridge, does it offer implementation speed rather than more generic advice?

## Rejection rule
If the idea cannot become a visual argument with diagnosis, mechanism, antithesis, application, and behavior shift, reject or reframe it before writing.

A clean mental model is not enough. The post must help the reader understand why the problem exists and what stronger operators do differently.
